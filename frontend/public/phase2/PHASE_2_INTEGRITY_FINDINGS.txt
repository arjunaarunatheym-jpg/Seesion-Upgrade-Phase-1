2. READ-ONLY LEGACY INVOICE STATUS AUDIT
----------------------------------------
Method: aggregate over the current `invoices` collection grouping by
(status, document_type). Zero writes performed.

Result (live database at audit time):
    status='paid'            document_type='invoice'    count=5
    status='issued'          document_type='invoice'    count=3
    status='draft'           document_type='invoice'    count=5
    status='deleted'         document_type='invoice'    count=2
    status='draft'           document_type='proforma'   count=1

    status='partial'                                    count=0
    status='partially_paid'                             count=0
    status='auto_draft'                                 count=0

Conclusion:
    - Legacy status "partial" does NOT exist in the current database.
      The canonical whitelist therefore stays:
          {issued, partially_paid, paid}
      NO backward-compatible alias `partial → partially_paid` was added.
      Previous documentation that suggested `partial` and `partially_paid`
      might be behaviourally equivalent has been REMOVED — the audit
      does NOT prove that.

    - `partially_paid` is used by the code path at
      routes/finance_payments.py (payment recording) but no rows carry
      that status in the current data snapshot. It remains reserved for
      future use and stays in the eligibility whitelist.

    - The code writes an `auto_draft` status at
          routes/finance_invoices.py:736
          routes/finance_invoices.py:804
      (auto-generated drafts). No records currently carry that status,
      but to avoid noisy `UNRECOGNIZED_INVOICE_STATUS` warnings the
      canonical service now treats `auto_draft` as an informational
      (non-revenue-eligible) status alongside `draft`.

Statuses discovered in code paths that WRITE `invoice.status`:
    draft, auto_draft, issued, paid, converted, cancelled, voided, deleted

All of these are now in `KNOWN_INVOICE_STATUSES` for the source-of-truth
service.


3. PROFORMA-vs-INVOICE OBSERVATIONS (Phase 3 candidates — DEFERRED)
-------------------------------------------------------------------
3a. `routes/finance_invoices.py::convert_proforma_to_invoice` correctly
    sets `converted_from_proforma_id` on the resulting invoice and marks
    the proforma `status = "converted"`. Where the link exists, Phase 2
    counts the pair once (single revenue).

3b. Historical proformas created before this convention (if any) may
    lack `converted_from_proforma_id`. Phase 2 surfaces this safely via
    the `PROFORMA_UNLINKED_MATCH` warning — it does NOT auto-repair.
    The repair belongs to Phase 3.

3c. `routes/finance_payments.py::create_session_credit_note` at line 1124
    uses `find_one({"session_id": session_id})` to pick a single invoice
    per session. When a session has multiple invoices this is ambiguous
    and CAN pick the wrong document.
    STATUS: IDENTIFIED and DEFERRED to Phase 3.
    (This corrects a previous statement that said the ambiguity is
    "reported through the session snapshot" — no such warning is emitted
    by the current service.)
