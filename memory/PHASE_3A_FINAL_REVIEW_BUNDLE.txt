Payment reversal (POST /superadmin/payment-reversal/execute):

# 7. CANONICAL SESSION → INVOICE RESOLVER RULES
################################################################################

resolve_session_primary_invoice(session_id, explicit_invoice_id=None):
    1. If explicit_invoice_id provided:
           - invoice must exist.
           - invoice.session_id must equal session_id.
           - invoice.document_type must not be proforma.
           - return that invoice.
    2. Else if session.invoice_id is set:
           - if the referenced invoice exists, has the right session_id, and
             is not a proforma, return it.
    3. Else search real non-terminal invoices for the session:
           - if EXACTLY one candidate exists, return it.
           - if none exist, raise NO_ELIGIBLE_INVOICE.
           - if multiple exist, raise AMBIGUOUS_SESSION_INVOICE_SELECTION
             with the candidate list.

Never uses find_one({"session_id": ...}) as authoritative anywhere.

# 8. PROFORMA IDEMPOTENCY IMPLEMENTATION
################################################################################

Endpoint POST /api/finance/invoices/{invoice_id}/convert-to-invoice:

    1. Load proforma. Confirm document_type == "proforma".
    2. guard.find_existing_conversion(proforma_id):
           existing = db.invoices.find_one(
               {"converted_from_proforma_id": proforma_id})
       If existing → return {idempotent: true, new_invoice_id, new_invoice_number}.
    3. If proforma.status in {"converted", "cancelled"}
           and no linked invoice found → HTTP 400 (terminal state).
    4. Insert new invoice. On IntegrityError (concurrent race),
       re-check find_existing_conversion and return that.
    5. Update the proforma with a filter that includes
           {"status": {"$ne": "converted"}}
       so a concurrent second update is a no-op.
    6. Update session.invoice_id.

Double-click / retry / concurrent request all return the same invoice — a
second real invoice is never created.

################################################################################
# 10. ACCOUNTING POSTING / REVERSAL RULES  (Section X)
################################################################################

- Payment journal:      posted once inside record_payment (existing behaviour).
- Payment reversal:     reverse/offset by marking the payment journal
                        status = voided; NEVER hard-delete accounting rows.
- Credit-note journal:  posted only when CN.status transitions to "issued".
                        Manual CN starts as draft — no journal.
- Credit-note void:     void the linked issued-CN journal by marking it
                        status = voided (idempotent).
- Invoice void/cancel:  respects existing accounting postings — nothing is
                        auto-deleted; existing payment-reversal flow handles
                        related journals when payments are reversed first.
- Idempotency:          every void operation is filtered by
                        {"status": {"$ne": "voided"}} so retries are safe.
