PROFORMA-vs-INVOICE observations (Phase 3 candidates)
-----------------------------------------------------
1. `routes/finance_invoices.py::convert_proforma_to_invoice` sets
   `converted_from_proforma_id` on the new invoice and marks the
   proforma `status = converted`. Where the link exists, Phase 2's
   session snapshot correctly counts once.

2. Historical proformas created before this convention (if any)
   may lack `converted_from_proforma_id`. Phase 2 surfaces this
   safely via the PROFORMA_UNLINKED_MATCH warning — it does NOT
   auto-repair. That workflow is reserved for Phase 3.

3. `routes/finance_payments.py::create_session_credit_note` line 1124
   uses `find_one({"session_id": session_id})` to pick a single
   invoice per session. When a session has multiple invoices this is
   ambiguous. Phase 2 does not change this behaviour; it merely
   reports the ambiguity through the session snapshot.

4. `routes/finance_session.py::get_session_costing` reads only
   invoices with status IN {issued, partial, paid}. The new
   canonical service uses {issued, partially_paid, paid} (matching
   the app-wide status set). Behaviour equivalent — but a screen may
   still be relying on the older locally-computed value. Migrating
   frontend/reporting screens to the new canonical endpoint is a
   later, separate task.

DEFERRED TO PHASE 3

- Proforma → Invoice link repair for historical unlinked pairs

DEFERRED TO PHASE 4
