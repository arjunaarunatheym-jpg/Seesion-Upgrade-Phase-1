3. EXACT TEST-DB ISOLATION MECHANISM
------------------------------------
    a) At module import time, BEFORE any application module is imported:
           TEST_DB_NAME = os.environ.get("TEST_DB_NAME")
                       or f"{DB_NAME}_phase2_test"
    b) A recognizer function requires the name to contain '_phase2_test',
       or start with 'test_', or end with '_test' / '-test'.
    c) If the resolved TEST_DB_NAME is not recognized, or equals the
       production DB_NAME, the module raises RuntimeError and pytest
       collection aborts — no fixtures can execute.
    d) `os.environ["DB_NAME"] = TEST_DB_NAME` is set BEFORE `server` is
       imported, so `core.db` binds to the isolated test DB.
    e) A runtime check inside the `app_client` fixture asserts that
       `core.db.name == TEST_DB_NAME`; if some earlier test file imported
       core with a different DB_NAME, the suite refuses to run.
    f) The production `.env` file is NEVER modified. Only the pytest
       process's environment variable is set.

    Production execution prevention (proof):
        - Direct attempt with TEST_DB_NAME="driving_training_db":
              raises RuntimeError with "not a recognized test database".
        - Direct attempt with an arbitrary name like "random_prod_db":
              also raises RuntimeError.
        - Setting TEST_DB_NAME == DB_NAME (case-insensitive) raises a
              dedicated RuntimeError refusing to touch production.
