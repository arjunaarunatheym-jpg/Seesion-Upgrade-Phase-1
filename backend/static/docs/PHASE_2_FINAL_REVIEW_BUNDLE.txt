Phase 2 — Canonical Financial Model
====================================

1. DOCUMENT FACE VALUE
   = invoices.total_amount

2. INVOICE ELIGIBILITY FOR REVENUE
   STRICT whitelist:
     include if:
       document_type != "proforma"
       AND normalized_status IN {issued, partially_paid, paid}
     exclude EVERYTHING else, including:
       - draft, auto_draft (informational, not yet a financial doc)
       - voided, cancelled, deleted, converted
       - proforma (any status)
       - any unknown/legacy status (triggers UNRECOGNIZED_INVOICE_STATUS)
   Known invoice statuses (KNOWN_INVOICE_STATUSES):
     draft, auto_draft, issued, partially_paid, paid,
     voided, cancelled, deleted, converted
   Note: legacy status "partial" was AUDITED against the live DB and found
   to have 0 records — no alias was added.
   For a non-eligible invoice:
     net_invoiced_value = 0
     outstanding_amount = 0
     payment_status = one of:
       n/a_proforma | n/a_draft | n/a_auto_draft | n/a_unknown
       voided | cancelled | deleted | converted
     Payments and Credit Notes on such invoices are preserved (never
     written), and NON_ELIGIBLE_INVOICE_HAS_ACTIVITY is emitted when any
     active activity exists.

3. CREDIT NOTE ADJUSTMENT
   STRICT whitelist:
     Active statuses (reduce net):   {draft, approved, issued}
     Inactive statuses:              {voided, deleted, cancelled}
     Any other status (typo, legacy unknown, missing/null/blank)
        -> NOT active, does NOT reduce net
        -> emits UNRECOGNIZED_CREDIT_NOTE_STATUS warning
   Legacy audit: 0 rows with missing status in the live DB → safest
   canonical treatment is to treat missing/null as unrecognized.
   Underlying CN record is preserved (service never writes).

4. NET INVOICED VALUE (per invoice)
   = document_face_value − sum(active_credit_notes)
   Proformas contribute 0.

5. VALID PAYMENTS (per invoice)
   Include payment if status != "reversed"

6. PAID AMOUNT
   = sum of valid payments attributable to the invoice

7. OUTSTANDING (per invoice)
   = max(0, net_invoiced_value − paid_amount)
   Overpayment is preserved separately (never silently normalized).

8. SESSION REVENUE
   = sum of NET_INVOICED_VALUE across all revenue-eligible invoices in the session
   Proformas NEVER contribute.
   Proforma + Invoice with converted_from_proforma_id link => counted ONCE.
   Ambiguous proforma+invoice pair with same face value and no link =>
     counted ONCE (proforma excluded) + PROFORMA_UNLINKED_MATCH warning.

9. SESSION COST
   = trainer_fees + coordinator_fees + expenses + marketing_and_admin
   (existing records — Phase 2 does NOT re-derive them.)

10. GROSS PROFIT
    = SESSION_REVENUE − SESSION_COST

11. GROSS MARGIN %
    = GROSS_PROFIT / SESSION_REVENUE * 100  (0 when revenue is 0)

12. INTEGRITY WARNING CODES (informational, non-destructive)
    PROFORMA_UNLINKED_MATCH             ambiguous proforma+invoice pair
    MULTIPLE_ACTIVE_PROFORMAS           more than one non-converted proforma in a session
    PAYMENT_MISSING_INVOICE             payment.invoice_id points to a missing invoice
    CN_MISSING_INVOICE                  credit note.invoice_id points to a missing invoice
    NET_NEGATIVE_AFTER_CN               credit notes exceed invoice face value
    OVERPAYMENT                         paid > net invoiced
    VOIDED_INVOICE_HAS_ACTIVE_PAYMENTS  invoice is voided/cancelled but has active payments
    DUPLICATE_INVOICE_NUMBER            same invoice_number appears more than once in a session
    UNRECOGNIZED_INVOICE_STATUS         invoice.status is outside the known set
    UNRECOGNIZED_CREDIT_NOTE_STATUS     credit_note.status is outside {draft,approved,issued,voided,deleted,cancelled}
    NON_ELIGIBLE_INVOICE_HAS_ACTIVITY   non-eligible invoice has active payments or credit notes

2. READ-ONLY LEGACY INVOICE STATUS AUDIT
----------------------------------------
Method: aggregate over the current `invoices` collection grouping by
(status, document_type). Zero writes performed.

Result (live database at audit time):
    status='paid'            document_type='invoice'    count=5
    status='issued'          document_type='invoice'    count=3
    status='draft'           document_type='invoice'    count=5
    status='deleted'         document_type='invoice'    count=2
    status='draft'           document_type='proforma'   count=1

    status='partial'                                    count=0
    status='partially_paid'                             count=0
    status='auto_draft'                                 count=0

Conclusion:
    - Legacy status "partial" does NOT exist in the current database.
      The canonical whitelist therefore stays:
          {issued, partially_paid, paid}
      NO backward-compatible alias `partial → partially_paid` was added.
      Previous documentation that suggested `partial` and `partially_paid`
      might be behaviourally equivalent has been REMOVED — the audit
      does NOT prove that.

    - `partially_paid` is used by the code path at
      routes/finance_payments.py (payment recording) but no rows carry
      that status in the current data snapshot. It remains reserved for
      future use and stays in the eligibility whitelist.

    - The code writes an `auto_draft` status at
          routes/finance_invoices.py:736
          routes/finance_invoices.py:804
      (auto-generated drafts). No records currently carry that status,
      but to avoid noisy `UNRECOGNIZED_INVOICE_STATUS` warnings the
      canonical service now treats `auto_draft` as an informational
      (non-revenue-eligible) status alongside `draft`.

Statuses discovered in code paths that WRITE `invoice.status`:
    draft, auto_draft, issued, paid, converted, cancelled, voided, deleted

All of these are now in `KNOWN_INVOICE_STATUSES` for the source-of-truth
service.


3. PROFORMA-vs-INVOICE OBSERVATIONS (Phase 3 candidates — DEFERRED)
-------------------------------------------------------------------
3a. `routes/finance_invoices.py::convert_proforma_to_invoice` correctly
    sets `converted_from_proforma_id` on the resulting invoice and marks
    the proforma `status = "converted"`. Where the link exists, Phase 2
    counts the pair once (single revenue).

3b. Historical proformas created before this convention (if any) may
    lack `converted_from_proforma_id`. Phase 2 surfaces this safely via
    the `PROFORMA_UNLINKED_MATCH` warning — it does NOT auto-repair.
    The repair belongs to Phase 3.

3c. `routes/finance_payments.py::create_session_credit_note` at line 1124
    uses `find_one({"session_id": session_id})` to pick a single invoice
    per session. When a session has multiple invoices this is ambiguous
    and CAN pick the wrong document.
    STATUS: IDENTIFIED and DEFERRED to Phase 3.
    (This corrects a previous statement that said the ambiguity is
    "reported through the session snapshot" — no such warning is emitted
    by the current service.)

Result (live DB at audit time)
------------------------------
    status        count
    ------------- -----
    'voided'          3
    'issued'          3
                  -----
    TOTAL             6

    null / missing / blank : 0

Code paths that WRITE credit_notes.status
-----------------------------------------
    routes/finance_payments.py:1032   compares status == 'approved'
    routes/finance_payments.py:1055   compares status != 'draft'
    routes/finance_payments.py:1300   compares status == 'voided'
    routes/superadmin_portal.py:1133,1320  status != 'voided' filters

Statuses observed in code:
    draft, approved, issued, voided

Conclusions
-----------
1. Legacy "partial" / "unknown" / null statuses DO NOT exist in the live
   credit_notes collection.
2. The canonical service uses a STRICT whitelist:
     ACTIVE_CN_STATUSES   = {'draft', 'approved', 'issued'}
     VOIDED_CN_STATUSES   = {'voided', 'deleted', 'cancelled'}
   Anything outside these two sets (including missing / null / blank) is
   NON-active and surfaced via UNRECOGNIZED_CREDIT_NOTE_STATUS.
3. Because 0 legacy CN rows have a missing status, the safest canonical
   treatment (missing status → unrecognized, does NOT reduce net) is
   applied without any backward-compat alias.
4. No production credit-note record was modified or deleted during this
   audit.
