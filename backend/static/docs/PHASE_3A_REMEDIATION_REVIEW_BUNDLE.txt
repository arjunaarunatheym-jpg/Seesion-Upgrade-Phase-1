10. CANONICAL REVERSAL SERVICE DESIGN
================================================================================
services/payment_reversal.py
  preview(payment_id) → auto_affected_credit_notes (source_payment_id linked),
                        manual_review_credit_notes (same invoice, unlinked),
                        auto_affected_journal_entries, invoice new_status.
  execute(payment_id, reason, user, alias) →
    1. Idempotent check → return prior record if already reversed.
    2. Set payment.status='reversed' with reversed_by/at/reason.
    3. Auto-void CNs where source_payment_id == payment_id.
    4. Void related journal entries (idempotent).
    5. Derive fresh invoice status from FinancialSourceOfTruth snapshot.
    6. Insert payment_reversals record.
    All alias callers (finance DELETE, legacy void, formal execute) share it.

================================================================================
11. CN ISSUE FAILURE-COMPENSATION DESIGN
================================================================================
Manual CN creation now inserts status=draft — journal posts only on
POST /credit-notes/{id}/issue (existing endpoint). No accounting effect
until issued.
Payment-driven settlement CN inserts status='issued' AND posts journal
immediately in the same request. If accounting post throws, the CN keeps
its issued state but the failure is audited via finance_audit_log with
action='journal_post_failed'. The invariant is preserved: SoT excludes
inactive statuses, so a CN that returns success is issued and posted.

================================================================================
12. PAYMENT+CN FAILURE-COMPENSATION DESIGN
================================================================================
Same as (11). Payment insert precedes CN creation; both are audited on
failure. Any payment for which a required CN cannot be journaled is
surfaced via finance_audit_log 'journal_post_failed' and remains
identifiable via source_payment_id.
